# Demo script (target 9:30, hard stop 10:00)

Before recording: `make reproduce` (or `make eval` with the substitutes fetched) so every file below exists;
`docker compose up` running; tabs open: the app (http://localhost:8000), `evals/samples/subP1/page.html`,
README status table, an editor on the repo. Every number said aloud is in the README status table.

| time | segment | show | say (one line each) |
|---|---|---|---|
| 0:00-0:45 | What it is | README top + status table | One agent: a beat grid you can trust, chat edits in beats and bars, audio -> a Web Audio page. The LLM interprets; code measures and executes. The test pack was missing: everything shown is SUBSTITUTE or generated audio, labelled. |
| 0:45-2:15 | **Click audition** (Part 1) | `uv run beat-agent analyze evals/substitutes/audio/gtzan_disco_00000.wav`; play `click_audition.wav` (accented click = downbeat); `grid_diagnostics.png`; a few lines of `grid.json` | Clicks sit on the kick. The grid JSON states its conventions (beat 0 = first downbeat, bars 1-based). On the generated 6-minute track the max drift is 0.91 ms, analysed in 8.5 s on a laptop CPU. On GTZAN the grid sits 12-17 ms before the human taps; the bias study shows the taps are late of the attacks, so no offset was added. |
| 2:15-3:30 | **Sync render** | `uv run beat-agent sync <6-min house> <partner> --at-bar 33` (generated pair from `evals/out/part1/_generated/`); play `overlap_mix.wav`, then `b_stretched.wav` alone | B is stretched with a Rubber Band time map, beat onto beat, not one global ratio. Measured kick offsets: median 1.7 ms, max 3.5 ms over 121 pairs. |
| 3:30-5:30 | **Two chat edits, one with pushback** | App: upload the disco substitute. (1) "Cut beat 16-32 and repeat it twice." -> read the echo; play; open the click audition of the edit; Undo. (2) "Chop out the boring part." -> the pushback. Optional: "Delete bars 200-210." | (1) The echo says what it did in beats, bars and seconds, and that "twice" means 2 plays in total, with the one-line alternative. The grid of the edit is mapped, not re-detected; re-tracking the edited audio agrees (beat F >= 0.98). (2) "Boring" is not measurable: it measures the quietest 3 bars, finds they are only 0.9 dB below average, says that is no basis, and cuts nothing until told. Out-of-range bars are rejected with the real bar count. |
| 5:30-7:00 | **Recreation next to its original** | `evals/samples/subP1/original.wav` then `page.html` (play, loop, mute drums); `score.json` | Demucs + band-split drums + Basic Pitch -> score JSON -> a fixed template; the LLM never writes JavaScript, and a test fails the build if a page contains a URL, fetch, import or audio data. Honest numbers: drum onsets F 0.72, labels F 0.33, render onsets F 0.98; it plays 14.5 ms late, explained in the render offset study. Chat changes ("mute the drums", "brighter bass", "play it at 140") are typed score ops: 3 of 3 applied. |
| 7:00-8:15 | **Code structure** | editor: `beat_agent/{analysis,edit,agent,transcribe,render,sync,app}`, `config.py`, `tests/test_no_hardcoding.py`, `evals/status.py` | Analysis -> grid JSON; edits are a clip timeline over the untouched source; the agent is a provider interface + pydantic plan + one retry; every threshold lives in config.py with its reason; the README status table is generated from eval files, so no number is typed by hand. |
| 8:15-9:30 | **Top 3 problems** | README "Known problems" | (1) Meter on hard material: fast 3/4 fails, 6/8 reads as 12/8, jazz locks to double time (downbeat F 0.07). (2) Part 3 drum labels are weak (F 0.33-0.48), and the render is 14.5 ms late. (3) Substitutes only, and the click check is weak outside S1: hard cuts flagged on 5 of 13 splices. |
| 9:30-10:00 | Close | `evals/README.md` committed vs regenerated | One command, `make reproduce`, rebuilds everything not committed. |

Fallbacks: if the LLM quota is out, cached sessions replay; S1/S4 in `evals/results/part2.md` show the same
echoes. If the app is slow to analyse, use `evals/out/part2/S1/turn1.wav` and its `transcript.md`.
