# evals

Everything here is regenerated by one command. Every number in the top-level README comes from a file
in `evals/results/`, which these scripts write.

> The official test pack was **not available** while this was built. Results come from **SUBSTITUTE**
> clips (public datasets, labelled as such in every table) and **generated** audio with exact ground
> truth. No parameter was tuned to a substitute. When `testpack/` is present, the same commands measure it
> and the test-pack rows replace the `missing` ones.

## Commands

| command | what it does |
|---|---|
| `make reproduce` | clean clone -> everything: `make substitutes`, then `make eval` |
| `make substitutes` | downloads the GTZAN excerpts + annotations (`evals/substitutes/fetch.py`) and builds the Part 3 substitutes from public MIDI with FluidSynth (`evals/substitutes/fetch_midi.py`) |
| `make eval` | deletes `evals/out` and `evals/results`, runs robustness, Part 1, Part 2, Part 3, the two root-cause studies, copies the licence-cleared samples, regenerates the README status block |
| `make eval-part2` | Part 2 chat sessions only (real Gemini, cached) |
| `python -m evals.status` | README status block from `evals/results/*.json` |

Inside Docker: `docker compose run --rm app make reproduce`.

## What is committed and what you regenerate

| path | committed? | why / how to get it |
|---|---|---|
| `evals/results/*.md`, `*.json` | **yes** | the reports: numbers, chat transcripts, LLM usage. Regenerated by `make eval` |
| `evals/samples/subP1/` | **yes** | Groove MIDI (CC BY 4.0) 2-bar drum loop: input render, reference MIDI, score JSON, Web Audio page, offline render, `ATTRIBUTION.md`. Regenerated by `make eval` (`python -m evals.samples`) |
| `evals/manifest.yaml`, `*.py` | **yes** | the harness itself |
| `evals/substitutes/audio/`, `annotations/` (GTZAN) | **no** | no licence stated. `make substitutes` |
| `evals/substitutes/part3/` (all four MIDI renders, the soundfont, FluidSynth) | **no** | Lakh / POP909 excerpts transcribe commercial songs the dataset licences do not cover; subP1's copy lives in `evals/samples/`. `make substitutes` |
| `evals/out/` (edited audio, click auditions, hard-cut controls, grids, stems, pages, renders) | **no** | derived from the clips above (GTZAN-derived audio must not be committed). `make eval` |
| `evals/llm_cache/` (the Gemini answers the committed results replay) | **yes** | one JSON per answer: text, token counts, model, fetch time; checked for secrets by `python -m evals.cache_tool check` and `tests/test_llm_cache.py`; pruned to what `evals/results` uses by `python -m evals.cache_tool prune` |
| `.cache/` | **no** | local decode / upload caches only |

### The Part 3 substitute renders are pinned

The MIDI excerpts are rendered to audio on your machine, so the renderer is part of the input:

| | pinned | where |
|---|---|---|
| FluidSynth | **2.3.1** (Debian bookworm `fluidsynth` / `libfluidsynth3` **2.3.1-2**) | `Dockerfile`; `fetch_midi.FLUIDSYNTH_VERSION` (the Windows fallback downloads the 2.3.1 build) |
| soundfont | **`TimGM6mb.sf2`** from `timgm6mb-soundfont` **1.3-5**, sha256 `c5378b62028c920cb11e4803327983fee2f2cdff5dc89c708e39da417e51c854` | `Dockerfile` (`sha256sum -c` at build); `fetch_midi.SF2_SHA256` (a mismatch is an error) |

`fetch_midi` records the FluidSynth version and soundfont checksum it used in `clips.json`, and `part3.md`
says whether they match the pin. **The committed Part 3 numbers come from the Docker image.** Measured: the
same MIDI rendered by FluidSynth 2.4.4 instead of 2.3.1 differs by 50-63 dB below the signal, enough to move
one note on subP3 and subP4 (pitched F 0.6222 vs 0.625); the Windows 2.3.1 build gets within 66-75 dB on
subP1-subP3 but is still not bit-identical (subP4 51 dB), so only the Docker image reproduces the committed
numbers exactly.

The licence reasoning per dataset is DECISIONS.md D20. Which Part 3 substitute may be committed is a field
in the manifest (`commit_outputs`), not a code path.

## LLM runs

**Results are replays of the committed cache by default.** The committed Part 2 and Part 3 chat results
replay the answers in `evals/llm_cache/`, fetched from `gemini-3.1-flash-lite` (free tier) on 2026-10-12
UTC; `part2.md` and `part3.md` each print a provenance line (model, replayed vs fetched live, fetch dates),
and every answer's cache key is in the JSON, so you can see exactly which file each turn replayed.

| eval mode | how | effect |
|---|---|---|
| **replay (default)** | `LLM_CACHE` unset or `replay` | committed answers only; no key, no API call; a prompt not in the cache is an error, and the run is withheld as partial |
| replay + fill gaps | `LLM_CACHE=on` | committed answers replayed; a prompt not in the cache is sent to the API (needs a key) and cached (e.g. after adding test-pack sessions) |
| live | `LLM_CACHE=off`, `make eval-live`, or `python -m evals.run part2 --live` | every call goes to the API with your key; fresh answers replace the cached ones, and results **may differ slightly** from the committed ones |

`LLM_CACHE` is read by the eval harness only. The preview app and `beat-agent chat` always make live calls
with your key and never read or write `evals/llm_cache/`; without a key they say how to add one.

In Docker: `docker compose run --rm -e LLM_CACHE=off app make eval`.

A full run makes **20 calls**: 17 Part 2 turns (10 sessions) and 3 Part 3 chat turns, up to 40 if every
answer needs its one validation retry. Answers are cached on (model, prompt, grid state, schema), so a
second run makes none, and any change to the analysis that changes the grid summary the model sees means
new calls. Set `GEMINI_MODEL` to any Gemini 3 model to re-run with another. Cache entries hold only the
model's JSON answer, token counts, the model name and the fetch time -- no key or request headers
(`tests/test_llm_cache.py`).

If the quota runs out mid-run, the eval stops calling, writes `evals/out/part2/part2.partial.json` (or
`evals/out/part3/part3.partial.json`) and leaves `evals/results/` as it was. Run it again after the reset:
the answers that arrived are replayed from the cache.

## Files

| file | measures |
|---|---|
| `robustness.py` | 36 generated cases (tempo, meter, swing, intros, steps, ramps, noise, formats); pass / partial / fail |
| `part1.py` | beat / downbeat F (mir_eval), drift, tempo type, meter, speed, sync kick alignment |

| `bias_study.py` | root cause of the grid's offset to human annotations (DECISIONS D16) |
| `render_offset_study.py` | root cause of the Part 3 render's onset offset (DECISIONS D21) |
| `synth.py` | generated audio with exact truth |
| `references.py`, `manifest.yaml` | clip resolution, references, sessions |
| `samples.py` | copies licence-cleared Part 3 outputs to `evals/samples/` |

## Failure analysis per clip

Numbers from `evals/results/part1.md`, `robustness.md`, `part2.md`, `part3.md`. SUBSTITUTE throughout.

### Part 1 (GTZAN substitutes)

- **sub-disco, sub-hiphop** -- beat and downbeat F 1.0, but a mean signed offset of -12 / -17 ms against
  the annotations. The bias study shows the annotations sit 11-22 ms after the audio's own attacks and the
  tracker within 3-5 ms of them; Beat This!'s official output has the same offset. Annotation convention,
  not a pipeline bug; no offset added.
- **sub-rock** -- beat F 0.80, 51 of 61 reference beats matched, max drift 39 ms. A live band with tempo
  drift; the grid is (correctly) `variable`; the 10 unmatched beats were not analysed further.
- **sub-jazz** -- the worst clip: the tracker locks to about double the annotated tempo (244 vs 126 BPM)
  and the meter decoder reads 6/8; beat F 0.53, downbeat F 0.07. "The tempo is half that" (session S6)
  repairs the beat level in chat, but nothing does it automatically.
- **sub-country** -- beat F 0.96 after the standard 5 s trim but 0.80 untrimmed: the start of the clip is
  where it goes wrong. Max drift 62 ms.

### Generalisation (generated audio)

- **Fails (2 of 36):** fast 3/4 (`random_05` at 139 BPM read as 4/4, `random_08` at 150 BPM read as 6/8).
  Not yet diagnosed.
- **Partials (8 cases; some have several notes):** 6/8 reported as 12/8 hypermeter (4), constant-tempo
  grids that miss the 10 ms target with a max error of 11-20 ms (6), the eighth-note level in a slow 6/8
  (1), and 200 BPM tracked at 100 with the x2 alternative offered (1).

### Part 2

- All 17 turns produced the intended operation (applied / proposal / clarify / error with the real limits).
  Two caveats: the model chose a `linear` fade in S1 where the documented default is equal-power (the echo
  states the shape); and S6 on jazz halves the tempo correctly to 122 BPM, but because the meter was already
  misread as 6/8, the halved grid has 3 beats per bar on a track annotated in 4/4.
- Clicks: 0 of 13 crossfaded splices flagged, but the hard-cut control is flagged on only 5 of 13 (all in
  S1), so on the other clips the detector cannot tell a click from the music. Listen to `turn*.wav` vs
  `*_HARDCUT_negative_control.wav` in `evals/out/part2/` after `make eval`.

### Part 3 (public-MIDI substitutes, rendered with a GM soundfont)

- **subP1 (Groove, 2-bar drums)** -- drum onsets P 0.86 / R 0.62 (36 found, 50 in the reference; which
  hits are missed was not analysed); by class only F 0.33, kick/snare/hat labels are often wrong. The render
  is a median 14.5 ms late; see `render_offset_study.md` (quantise towards a late grid + compressor
  look-ahead, not synth attack shape). The 2-bar clip is too short for meter decoding, so 4/4 is assumed for
  bar labels only.
- **subP2 (Lakh, drums + bass)** -- every reference drum hit is found (R 1.0) but with 25 extra hits
  (P 0.65); bass F 0.88. Chat changes: 3 of 3 applied.
- **subP3 (POP909, piano)** -- pitched F 0.62: Basic Pitch finds 142 notes for 83 in the reference (P 0.49,
  R 0.84; the kind of extra notes was not analysed), and the meter reads 6/8 (whole-clip loop mode
  keeps the loop length right regardless). Render onset F 0.71, the lowest.
- **subP4 (Lakh, dense mix)** -- no reference is used, as in the brief; render onset F 0.93 against the
  original's own onsets.
- These renders are much cleaner than real recordings, so the numbers are likely optimistic for the real
  P1-P4.
